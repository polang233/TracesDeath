# 遗体核心设计

目标流程：死亡掉落接管 → 躺卧 Mannequin → 固定槽位 GUI → 领取 → 取空消失。

## 所有权

- `Corpse` 保存一具遗体的身份、位置、皮肤、原始槽位和待完成领取。主手只是选中的快捷栏槽，没有额外库存副本。
- `CorpseItems` 负责死亡掉落与原始槽位匹配、GUI 槽位映射、无副作用的领取数量计算。
- `CorpseStore` 负责严格读取、同步文件写入与原子替换。保存失败抛出异常，不自行修改内存。
- `CorpseService` 在服务器线程串行执行死亡接管、领取和恢复。先保存候选状态，再发布到内存。
- `CorpseEntities` 维护非持久化实体。实体只展示记录，不能发放物品。
- `CorpseMenu` 展示库存副本，保存查看会话。点击下一 tick 进入领取流程，关闭界面不写库存。

## 领取状态

活动库存先转换为带 `PendingClaim` 的记录。记录包含领取者 UUID、领取前后 36 格背包快照、遗体领取后的槽位内容。写入成功后才修改玩家背包。

玩家保存后，写入完成状态；遗体有剩余则恢复活动状态，没有剩余则保留空的完成标记。待完成领取既锁定对应遗体，也阻止同一玩家从其他遗体领取。任何保存失败都不会用停服时的旧缓存覆盖磁盘。

登录时按实际背包恢复待完成领取。无法判断时保留记录，需要控制台明确发放结果。任何重试只能完成当前记录，不能重复调用发物品操作。

## 取舍

本版选择非持久化真实实体，由 Paper 负责跟踪与交互。外观无需与世界实体存档保持第二份持久状态。实体的创建失败不影响已保存库存，后续修复任务重试；清理不决定库存是否重新可领取。

保存采用包含待完成状态的原子 YAML 记录，保持首版依赖与部署简单。相比 SQLite，它仍需同步写文件，不能提供跨多个记录的事务，也无法把玩家存档纳入同一事务。若未来规模或审计需求增加，应替换保存实现，不改变槽位和领取语义。

固定槽位以实际掉落为准匹配，数量逐份消耗。相同物品有多份而其他插件只保留其中一份时，死亡事件不提供足以区分其原槽位的信息；数量保持一致，具体槽位按顺序匹配。

## 生命周期验收

必须验证：背包满和部分空间、多人争抢、距离改变、关闭与断线、取空、keepInventory、区块卸载/加载、实体被移除、重启恢复、准备/完成阶段写入失败、损坏数据拒绝加载。正常运行只由已加载区块创建实体，不强制加载区块。

仍需真人客户端验收：四个朝向、不同皮肤和皮肤层、台阶/斜坡/水中与区块边界处的视觉和点击范围。服务端 API 测试和假客户端不能替代这些视觉检查。
