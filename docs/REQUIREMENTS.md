# TracesDeath 可行需求文档（重基线）

> 文档版本：v2.0
> 更新时间：2026-08-28
> 文档状态：开发基线，待产品确认
> 目标运行环境：Paper 26.2 / Minecraft 26.2 / Java 25
> 审阅基线：当前 HEAD 加当前工作树未提交改动
> 参考产品：[AxGraves](https://github.com/Artillex-Studios/AxGraves)

## 0. 结论先行

TracesDeath 的首个可发布版本只承诺一条稳定链路：

玩家死亡 → 接管物品 → 在安全位置生成方块标记 → 虚拟背包领取 → 持久化/过期清理

本版本采用“一个墓碑记录、一份权威物品数据、一个存储适配器”的原则：

- mannequin 是默认主类型：Mannequin 负责玩家外观，独立 Interaction 实体负责稳定点击；block 作为兼容回退。
- 普通右键打开 GUI；潜行右键执行快速领取。两种入口共享同一套领取逻辑。
- 服务器重启、配置重载、GUI 关闭、断线、过期和管理员移除都必须满足物品不丢失、不复制。
- minecart、corpse 和 custom_entity 已从当前运行时移除，后续只有重新立项并通过同一套守恒测试才会恢复。

当前需求文档不再把“已有类、已有配置项”和“已验收能力”混为一谈。存在代码只代表有实现痕迹，不代表可以发布。

## 1. 目标与非目标

### 1.1 产品目标

TracesDeath 是一个 Paper 服务端死亡物品保护插件。玩家死亡后，本应散落在世界中的物品被集中保存到死亡地点附近的墓碑中，玩家可以回到墓碑取回物品，管理员可以查询、清理和处理异常墓碑。

成功标准：

1. 创建成功后，原生掉落不再出现，墓碑中的物品与被接管的物品完全一致。
2. 创建失败时，插件不改变原生掉落，不覆盖重要方块，不留下无法管理的孤儿数据。
3. 任何领取路径都按实际数量更新墓碑；部分堆叠、背包满、重复点击和多人访问不能造成物品丢失或复制。
4. 正常停服和重启后，活动墓碑仍可查询、领取和按原创建时间过期。
5. 所有稳定版配置项都有真实行为、明确默认值和可测试的验收标准。

### 1.2 非目标

首个稳定版本不包含：

- 跨服务器或数据库集群共享墓碑。
- 经济赎回、保险、邮寄、跨服传送等玩法。
- 完整尸体动画、客户端模组资源或数据包渲染。
- 通用自定义实体注册。
- 依赖 NMS、数据包跟踪或 AxGraves 私有 API 的实现。

## 2. 参考 AxGraves 后提炼的设计原则

AxGraves 的核心可借鉴点不是具体 API，而是把一个墓碑当成完整聚合对象：物品、经验、时间、显示实体、交互和移除都围绕同一对象管理；它还提供普通打开与潜行快速领取、7 格距离限制、保存恢复、过期处理、每玩家墓碑上限、世界/死亡原因/物品过滤和细分权限。相关行为可从其 [Grave](https://github.com/Artillex-Studios/AxGraves/blob/master/src/main/java/com/artillexstudios/axgraves/grave/Grave.java)、[config.yml](https://github.com/Artillex-Studios/AxGraves/blob/master/src/main/resources/config.yml) 和 [DeathListener](https://github.com/Artillex-Studios/AxGraves/blob/master/src/main/java/com/artillexstudios/axgraves/listeners/DeathListener.java) 看到。

TracesDeath 采用以下借鉴结论：

| AxGraves 的做法 | TracesDeath 的采用方式 |
|---|---|
| 一个墓碑对象统一管理内容和生命周期 | 引入统一 GraveRecord，管理器只操作记录，不在事件类中拼接状态 |
| 普通交互打开库存，潜行交互快速领取 | 默认右键 GUI、潜行右键快速领取；保留单一领取服务 |
| 打开距离限制 | 稳定版默认限制为 7 方块，超出距离关闭 GUI |
| 保存开关和自动保存 | 保留立即保存、周期保存、停服保存，重写为可恢复的原子写入 |
| 物品顺序、护甲自动装备、背包差额处理 | 保留能力，但必须按 addItem 的真实剩余量更新 |
| 世界、死亡原因、物品过滤 | 作为 P1 配置能力加入，不影响 P0 主链路 |
| 每玩家墓碑数量和权限节点 | 作为 P1 管理能力加入 |

不直接照搬的部分：

- AxGraves 的 NMS/数据包实体、全局静态状态和第三方 AxAPI 不纳入当前工程。
- AxGraves 现有文件写入方式不等于本项目的可靠性标准；本项目要求版本化、原子替换、损坏隔离和失败可恢复。

## 3. 当前代码审视

### 3.1 当前代码已经提供的能力

| 模块 | 当前代码 | 结论 |
|---|---|---|
| 死亡监听 | PlayerEvents 接收 PlayerDeathEvent，读取掉落物并调用 TraceManager | 主流程存在，但缺少权限、keepInventory 覆盖和事务回滚 |
| 方块墓碑 | BlockContainerTraceProvider 支持箱子、木桶、潜影盒并写入 PDC | 可作为稳定版基础，需先修复安全放置和数据原子性 |
| 虚拟 GUI | TraceGuiManager 提供 54 格界面和关闭同步 | 当前会截断物品、允许变相存入并可能把特殊物品误判为装饰物 |
| 快速领取 | TraceInteractEvents 支持 DIRECT_COLLECT 和自动装备 | 部分堆叠时会丢失剩余数量，需重写为差额结算 |
| 缓存持久化 | TraceCacheManager 使用内存缓存加墓碑 YAML 文件 | 有基本恢复能力，但无 schema、原子写入，异步任务直接操作 Bukkit 对象 |
| 生命周期 | TraceManager 支持活动索引、定时过期和管理员移除 | 删除顺序、过期提醒、实体/方块校验和幂等性不足 |
| 管理命令 | 支持 reload/types/list/info/remove/clear/debug create | 基础命令存在，但消息硬编码、只识别完整 UUID，权限粒度不足 |
| 保护事件 | Mannequin 伤害、死亡掉落、火焰和熔岩已拦截 | block 回退类型只保留基础熔岩保护 |
| 实体提供者 | 只保留 Mannequin，并用 Interaction 作为点击代理 | 两个实体 UUID 均持久化、重启校验并统一删除 |
| 测试 | 仓库没有测试源码 | 物品守恒和重启恢复没有自动化发布门槛 |

### 3.2 重基线时发现的结构性问题

1. 方块使用缓存，矿车使用实体原生库存，尸体还写入实体 PDC，形成多份物品副本。
2. TraceManager 先放置世界对象，再写持久化数据；写入失败时可能留下墓碑而死亡事件仍被清空。
3. GUI 固定 54 格，装备最多 9 个、普通物品最多 36 个，超出的物品会消失在界面同步之外。
4. GUI 没有墓碑级会话锁，也没有完整禁止 Shift 点击、双击收集和拖拽存入。
5. 快速领取用“是否存在空位”预判库存，未结算 addItem 返回的部分剩余量。
6. 多个事件类按当前全局 storage.type 读取配置，重载后可能用新类型规则处理旧墓碑。
7. tracesdeath.use、warn-before-expire、warn-time-seconds、allow-break、explosion-proof 和 buoyant 虽然有配置或字段，但行为不完整。
8. minecart 与缓存同时保存同一批物品；corpse 的实体库存服务当前不是统一缓存链路。
9. 现有 clear-drops=false 会让缓存物品和原生掉落同时存在，属于明确的复制风险。
10. 现有 force-place=true 可能覆盖死亡点的重要方块；稳定版不能以“强制放置”换取创建成功。

### 3.3 首轮实施状态

- 已移除矿车、盔甲架尸体、自定义实体占位和对应的第二库存链路。
- Mannequin 与 Interaction 点击代理成对创建，并持久化两个实体 UUID。
- NPC 删除会清空视觉装备、删除两个实体；区块重新加载时会清理孤儿或补齐缺失实体。
- 方块和 NPC 共用访问检查、分页只取 GUI、快速领取和实际库存差额结算。
- 初次数据写入使用临时文件原子替换；失败时回滚世界对象并保留原生死亡掉落。
- 已加入配置、数据隔离和提供者元数据单元测试。

## 4. 发布范围和阶段

### P0：稳定 Mannequin 墓碑闭环

- 只接管物品，不处理经验；在经验存储完成前不得清除死亡经验。
- 默认启用 mannequin，持久化视觉实体和交互代理 UUID；block 仅作兼容回退。
- 一个墓碑记录作为物品唯一权威来源。
- 支持安全创建、GUI 领取、潜行快速领取、过期、停服保存、重启恢复和管理员处理。
- 所有关键操作都有自动化测试和 Paper 测试服回归用例。

### P1：对齐 AxGraves 的常用体验

- 经验存储与领取。
- 世界、死亡原因、物品黑名单。
- 每个玩家的墓碑数量上限及权限覆盖。
- /td locate 或等价的墓碑定位反馈。
- 到期预警、掉落表现、可选全息提示。
- 更细的管理权限和管理员审计日志。

### P2：替代存储重新立项

corpse、minecart 或其他实体类型若重新加入，必须复用 P0 的 GraveRecord、领取服务、持久化、保护和清理协议，不能重新引入实体原生库存或第二份 PDC 物品。

custom_entity 继续作为不可用占位，不得静默回退到其他类型。

## 5. 用户流程

### 5.1 玩家死亡

1. 检查全局开关、玩家权限、世界和死亡原因过滤。
2. 从死亡事件取得物品快照；所有 ItemStack 深拷贝并保留完整 NBT、附魔、名称、Lore、耐久和数量。
3. 在搜索半径内寻找安全方块位置。不能覆盖非空气、非液体、容器、重要方块或插件明确保护的方块。
4. 先创建带墓碑 UUID 的方块标记，再写入持久化记录；任一步失败都回滚方块并保留原生掉落。
5. 只有记录已持久化成功后，才清空死亡事件中的原生物品掉落。
6. 创建成功后才播放音效、粒子和成功消息。

默认遵循游戏的 keepInventory。当 keepInventory=true 时，P0 不创建墓碑且不修改玩家库存；P1 再实现明确命名的 override-keep-inventory，并对第三方插件兼容性单独测试。

### 5.2 玩家领取

- 右键墓碑：打开虚拟 GUI。
- 潜行右键墓碑：执行快速领取；若关闭该选项，则按普通右键打开 GUI。
- 交互距离超过 7 方块时拒绝打开；已经打开 GUI 后离开范围、跨世界或断线时关闭并保存。
- owner-only=true 时，只有所有者和拥有管理员绕过权限的用户可以领取。
- 找不到缓存记录、UUID 无效或墓碑已终结时，取消原生容器交互并提示错误；不能打开一个空的普通箱子。

### 5.3 GUI 规则

- GUI 只展示墓碑物品，不使用依赖材质判断的装饰槽。
- 物品数量超过单页容量时分页；任何物品都必须可见、可领取、可恢复。
- GUI 默认只允许取出，不允许玩家向墓碑放入物品。
- 必须取消 Shift 点击、双击收集、拖拽、数字键交换、热键交换和关闭过程中的非法存入。
- 同一墓碑默认只允许一个玩家打开；其他玩家收到“正在被使用”的提示。
- 所有点击、拖拽、关闭、断线、死亡和插件停用路径都以服务端 GraveRecord 为准保存一次。
- GUI 只负责展示；不把 GUI、方块库存和实体库存同时作为数据源。

### 5.4 快速领取规则

按每个物品堆栈依次处理：

1. 启用自动装备且目标装备槽为空时先尝试装备。
2. 其余物品调用 Bukkit 的实际库存添加方法。
3. 以返回的剩余堆栈为准更新墓碑；不得用“存在空槽”推断整组物品都能放下。
4. 默认剩余物品留在墓碑中；若配置为掉落，只有实际剩余量掉落。
5. 消息显示实际领取数量和仍剩余数量。

当物品和经验（P1）都为空，且启用 despawn-when-empty 时，墓碑进入终结流程。

### 5.5 过期、移除和异常

- 过期时间使用绝对时间戳计算，服务器重启不重置。
- 到期时，剩余物品只能处理一次：drop 掉落或 delete 销毁，并记录墓碑 UUID。
- 过期前预警只发送一次；玩家离线时不补发刷屏消息。
- 管理员移除、批量清理、允许破坏和过期处理必须调用同一个幂等终结服务。
- 方块标记丢失时，持久化记录不能立即删除；系统应尝试恢复标记，失败则标记为 ORPHANED，保留物品并让管理员可查询和处理。

## 7. 数据模型和生命周期

### 7.1 GraveRecord

每条活动记录至少包含：

| 字段 | 说明 |
|---|---|
| id | 墓碑 UUID，持久化文件名和世界标记使用同一 ID |
| ownerId / ownerName | 所有者 UUID 和创建时名称 |
| worldId / x,y,z,yaw,pitch | 实际放置位置；世界 UUID 优先于世界名称 |
| createdAt / expiresAt | 创建时间和绝对到期时间；永不过期使用明确的空值或 0 |
| storageType | 创建时使用的提供者；配置重载不得改变旧墓碑类型 |
| items | 序列化后的物品条目，保留原始槽位或稳定顺序 |
| experience | P1 字段；P0 必须明确为 0 且不修改死亡经验 |
| state | ACTIVE、ORPHANED、EXPIRED、CLAIMED、REMOVED |
| warningSent | 是否已经发送到期预警 |
| schemaVersion | 数据格式版本，用于迁移和拒绝不兼容数据 |

TraceInfo 只能是记录的只读视图。方块/实体 PDC 只保存 id、storageType 和 ownerId 等索引元数据，不保存第二份可领取物品。

### 7.2 提供者协议

稳定版提供者至少需要：

- supports(config)：启动时判断是否可用。
- place(record)：创建标记并返回实际位置和可验证句柄。
- locate(record)：重启或区块加载后定位世界对象。
- isValid(record)：确认对象属于该墓碑 UUID。
- remove(record)：幂等移除对象，不处理物品。
- restore(record)：对象丢失时尝试恢复，不覆盖重要方块。

未支持的类型必须失败并保留原生掉落，不能自动回退到 block 或其他类型。

### 7.3 生命周期

CREATING → ACTIVE → CLAIMED / EXPIRED / REMOVED / ORPHANED → TERMINAL

- 只有世界标记、持久化记录和内存索引都成功后才进入 ACTIVE。
- 所有终结入口共享一个带状态检查的服务。
- 终结操作先冻结领取会话，再结算剩余物品，最后移除世界标记和记录。
- 重复终结只返回“已处理”，不重复掉落。

## 8. 配置需求

稳定版建议收敛为以下语义，现有未实现开关不能继续作为有效承诺：

| 配置 | 默认 | 说明 |
|---|---:|---|
| enabled | true | 是否接管新死亡 |
| storage.type | mannequin | 默认使用高版本玩家模型 NPC；block 是兼容回退 |
| storage.block.material | CHEST | block 回退类型必须使用已知容器方块 |

建议删除或暂时废弃：

- death.clear-drops：已删除；稳定版创建成功后固定清除，不能允许复制语义。
- death.clear-experience：已删除；当前没有经验墓碑，经验保持原版行为。
- placement.force-place：已删除；不能用覆盖重要方块来保证创建。
- types.*.buoyant：已删除，待未来明确水/熔岩语义后再设计。
- minecart、corpse 和 custom_entity 配置：已从默认配置和运行时注册中删除。

配置重载规则：

- 重载只影响新墓碑和明确允许动态变更的生命周期参数。
- 旧墓碑继续使用其记录的 storageType 和数据格式。
- 非法配置回退到文档化默认值并输出一次告警。
- 重载不得清空活动索引、删除世界标记或重置创建时间。

## 9. 命令和权限

主命令：/tracesdeath，别名 /td、/deathtrace。

| 命令 | 权限 | 说明 |
|---|---|---|
| /td | tracesdeath.use | 显示帮助 |
| /td list [玩家] | tracesdeath.use / tracesdeath.admin | 普通玩家默认只看自己；管理员可看全部或指定离线玩家 |
| /td locate [ID] | tracesdeath.use | 显示自己的墓碑位置和剩余时间 |
| /td reload | tracesdeath.admin | 重载配置和语言，不终结墓碑 |
| /td types | tracesdeath.admin | 显示稳定、实验性和不可用类型 |
| /td info <ID> | tracesdeath.admin | 支持完整 UUID 和无歧义前缀 |
| /td remove <ID> [drop|delete] | tracesdeath.admin | 幂等终结单个墓碑 |
| /td clear [drop|delete] | tracesdeath.admin | 批量终结并返回成功/失败数量 |
| /td debug create | tracesdeath.admin | 创建明确标记的测试墓碑，不扣除玩家物品 |

建议权限节点：

- tracesdeath.use
- tracesdeath.admin
- tracesdeath.admin.bypass
- tracesdeath.list.other
- tracesdeath.locate
- tracesdeath.debug

所有命令消息、拒绝原因、成功/失败结果和占位符都必须来自 lang.yml，不得在命令类中混入硬编码玩家文案。

## 10. 持久化与可靠性要求

1. 数据文件必须包含 schemaVersion，支持迁移；无法迁移的文件移动到隔离目录而不是覆盖。
2. 写入使用临时文件加原子替换；删除失败必须记录并可在下一次启动重试。
3. 创建、领取、清空、过期、移除和配置重载后的关键变更必须进入可靠保存队列。
4. 异步线程只能处理不可变序列化快照和文件 IO，不能直接读取或修改 Bukkit 世界、库存、实体和 ItemStack。
5. 单个坏文件不能阻断其他墓碑加载；日志至少包含墓碑 UUID、文件名、阶段和原因。
6. 内存索引和持久化数据必须以同一份 GraveRecord 为准；不能通过扫描当前全局类型猜测旧墓碑。
7. 正常停服时先关闭/同步所有 GUI 会话，再停止任务，最后保存数据；活动墓碑世界对象默认保留。
8. 创建失败、保存失败、恢复失败和对象丢失都必须有明确状态，不得静默删除记录。

## 11. 保护和边界行为

稳定版至少处理：

- 方块破坏、爆炸、火焰和熔岩。
- 漏斗、活塞、流体替换和原生容器打开绕过。
- 其他插件或管理员直接移除墓碑方块后的孤儿记录。
- 区块未加载时不强制加载大量区块；重新加载后再校验或恢复。

当前策略：

- Mannequin 和 Interaction 的玩家伤害事件始终取消。
- Mannequin 异常进入死亡事件时清空掉落和经验；活动墓碑会取消死亡并补齐实体。
- 外部移除活动 NPC 后按墓碑 UUID 重新校验并补齐；数据已不存在的实体在区块加载时删除。
- block 只作为兼容回退，禁止通过原生容器库存绕过虚拟墓碑库存。
- 领地插件兼容不作为 P0 强依赖。

| 编号 | 场景 | 预期 |

| AC-001 | 默认配置，玩家带普通物品死亡 | 生成一个方块墓碑；原生掉落清空；墓碑记录物品完全一致 |

## 14. 实施顺序

### 阶段 B：修复稳定主链路

1. 重写安全选址和原子创建。

4. 完成原子持久化、重启恢复、孤儿标记和重复终结保护。

### 阶段 C：完成运维体验

1. 权限分层、完整本地化、短 ID/离线玩家查询。

当前不继续扩展提供者。未来若恢复尸体或矿车，每次只启用一个新提供者，完成数据、交互、保护、恢复和物品守恒矩阵后再进入可选能力。

## 15. 待确认决策（附推荐值）

| 事项 | 推荐值 | 原因 |
|---|---|---|
| 稳定版默认存储 | mannequin | 符合项目目标；Interaction 代理解决躺卧 NPC 难点击问题 |
| GUI 是否允许存入 | 不允许 | 降低复制、误操作和外部库存绕过风险 |

| 实体展示装备 | 只做不可领取视觉副本 | 防止展示实体和墓碑记录产生第二份物品 |
| 实验类型可见性 | 默认禁用，types 显示状态 | 让服主知道类型存在，但不会误以为已稳定 |
