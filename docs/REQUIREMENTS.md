## 1. 文档目的

本文档用于统一 TracesDeath 的产品边界、行为规则、验收标准和后续开发优先级。

当前仓库已经具备死亡事件监听、方块墓碑、虚拟 GUI、缓存文件、管理命令以及多种存储提供者。未提交代码进一步增加了实际位置回传、正常停服保存、缓存索引恢复、所有者检查和 Mannequin 玩家模型墓碑，但部分配置仍只完成读取，部分存储类型仍使用不同的数据链路。因此，本文将“目标需求”和“当前实现状态”分开描述，不把已有代码等同于已通过验收的产品能力。

## 2. 产品概述

### 2.1 产品定位

TracesDeath 是一个 Minecraft Paper 服务端死亡物品管理插件。玩家死亡后，插件将本应掉落的物品集中保存到死亡地点附近的可交互“墓碑”中，让玩家能够返回现场取回物品，并让管理员能够查询和处理活动墓碑。

### 2.2 核心价值

- 降低死亡物品散落、烧毁或因实体过多造成服务器负担的风险。
- 为玩家提供清晰、可预期的遗物取回流程。
- 为服主提供可配置的过期、权限、保护和清理策略。
- 通过统一存储接口，为方块、矿车、尸体和玩家模型等外观保留扩展能力。

### 2.3 产品成功标准

- 一次死亡产生的每个物品，在墓碑创建、领取、过期、移除和重启恢复过程中均不得无故丢失或复制。
- 默认配置下，普通玩家无需管理员介入即可完成“死亡—定位墓碑—取回物品—墓碑清理”的完整流程。
- 服务器正常停止、异常退出或区块卸载后，仍能恢复并管理未结束的墓碑生命周期。
- 所有公开配置项都具有真实、可验证且跨存储类型一致的行为。

## 3. 用户与使用场景

### 3.1 用户角色

| 角色 | 目标 | 权限 |
|---|---|---|
| 普通玩家 | 死亡后安全取回自己的物品 | `tracesdeath.use` |
| 其他玩家 | 按服务器规则访问他人的墓碑 | `tracesdeath.use`，并受所有者策略限制 |
| 管理员/服主 | 配置、诊断、查询、移除和批量清理墓碑 | `tracesdeath.admin` |

### 3.2 核心场景

1. 玩家在普通地面、水中、熔岩附近或狭窄空间死亡，系统在合法位置创建墓碑。
2. 玩家点击墓碑，通过 GUI 逐件取回，或通过直接领取一次性恢复物品。
3. 玩家背包或装备槽存在冲突，系统按配置保留、转入背包或掉落物品。
4. 墓碑到期前提醒所有者，到期后按配置掉落或销毁剩余物品。
5. 服务器重启后，墓碑实体、物品数据、所有者和剩余时长继续有效。
6. 管理员查询玩家墓碑，查看详情，移除单个墓碑或清理全部墓碑。
7. 服主可选择使用玩家皮肤 Mannequin 展示死亡玩家外观，并通过统一虚拟背包取回遗物。

## 4. 范围

### 4.1 当前目标范围

- 玩家死亡物品接管。
- 方块容器墓碑的完整可用闭环。
- GUI 与直接领取两种交互方式。
- 墓碑所有者、保护、过期和持久化。
- 管理命令、可配置文案和调试日志。
- 可扩展的存储提供者接口。

### 4.2 后续扩展范围

- 箱子矿车墓碑。
- 玩家头颅盔甲架形式的尸体墓碑。
- Paper Mannequin 玩家模型墓碑。
- Paper API 能力成熟后的通用自定义实体墓碑。
- 与领地、经济、地图标记或跨服系统的集成。

### 4.3 暂不纳入

- 跨服务器共享墓碑。
- 数据库集群和多实例并发写入。
- 完整尸体动画或客户端模组资源。
- 为死亡物品提供经济赎回、保险或邮寄玩法。

## 5. 产品规则

### 5.1 唯一数据源

每个墓碑必须具有唯一 UUID。墓碑元数据、管理索引、交互界面和持久化文件必须指向同一份权威物品数据；不得同时把同一批物品独立保存在缓存、实体原生库存或实体 PDC 序列化库存中。

展示在 Mannequin 或其他实体身上的装备只能是不可领取的视觉副本，且实体被任何路径移除时都不得产生额外掉落。

### 5.2 物品守恒

对任意一次墓碑生命周期，应满足：

`接管的死亡物品 = 墓碑剩余物品 + 已被玩家领取物品 + 按规则掉落物品 + 明确配置为销毁的物品`

任何创建失败、库存溢出、并发打开、配置重载、服务器停止或恢复失败都不得破坏该规则。

### 5.3 生命周期状态

墓碑至少包含以下状态：

`创建中 → 活动 → 已清空 / 已过期 / 被管理员移除 / 容器丢失 → 已终结`

- 只有放置和数据保存都成功后，墓碑才可进入“活动”。
- 终结操作必须具备幂等性，重复执行不得重复掉落物品。
- 容器消失但数据仍在时，系统必须记录异常并按恢复策略处理，不能静默遗留孤儿数据。

### 6.3 墓碑数据模型

每个活动墓碑至少保存：

- 墓碑 UUID、存储类型和数据格式版本。
- 所有者 UUID 与创建时玩家名。
- 世界标识和墓碑实际坐标。
- 创建时间、到期时间或永不过期标记。
- 完整物品列表及其槽位语义。
- 当前生命周期状态和过期提醒状态。
- 对应方块或实体的可验证标识。

| 编号 | 需求 | 验收标准 | 当前状态 |
|---|---|---|---|
| FR-201 | 实际位置一致性 | 缓存、命令输出和清理逻辑使用提供者返回的实际放置位置，而非原始死亡位置 | 已实现于未提交代码；仍需测试各种提供者 |
| FR-202 | 槽位保真 | 主手、副手、护甲和普通背包物品可按原槽位记录；若仅保存无序物品，也必须保证所有物品均可见且可领取 | 部分实现；当前保存压缩列表 |
| FR-203 | 单一权威库存 | 方块、矿车、尸体和 Mannequin 统一通过同一数据服务读写，不产生缓存与实体库存双份数据 | 方块和 Mannequin 基本符合；尸体仍写入未使用的 PDC 副本，矿车仍使用原生库存 |
| FR-204 | 数据格式版本 | 持久化记录包含 schema version，并支持升级或拒绝不兼容数据且保留原文件 | 未实现 |
| FR-205 | 存储类型持久化 | 每条墓碑数据保存创建时的存储类型，重启和配置重载后仍可选择正确提供者 | 部分实现；已保存并用于管理清理，但交互/自动移除仍有全局类型分支 |

### 6.10 存储类型

| 类型 | 当前产品结论 | 当前实现与稳定版门槛 |
|---|---|---|
| `block` | 首要支持类型 | 主链路可用；完成 GUI、权限、保护、恢复校验及测试后进入稳定版 |
| `minecart` | 实验性 | 仍使用实体原生库存并同时建立缓存；需统一权威库存，补齐实体交互、所有权、移动位置更新和区块恢复 |
| `corpse` | 实验性 | 未提交代码已改由统一实体监听打开缓存 GUI；仍写入旧 PDC 物品副本，且实体点击不支持直接领取和点击方式配置 |
| `mannequin` | 新增实验性 | 已生成带玩家皮肤、姿势和展示装备的 Mannequin，使用缓存 GUI、所有者检查、实际位置及清理；需验证展示装备不掉落、配置交互、权限绕过、区块恢复和实体生命周期 |
| `custom_entity` | 预留且不可用 | Paper 提供稳定通用 API 后另立评审；当前选中时应明确失败，不应静默回退 |

### 6.12 管理命令

主命令：`/tracesdeath`；别名：`/td`、`/deathtrace`。

| 命令 | 需求 | 当前状态 |
|---|---|---|
| `/td reload` | 重载配置和语言；不得终结已有墓碑 | 部分实现；未提交代码已避免终结，但旧墓碑交互仍可能读取新全局类型 |
| `/td types` | 显示类型及状态：稳定/实验/不可用，而不只是注册 ID | 部分实现；会列出新增 `mannequin` ID，但无状态 |
| `/td list [玩家]` | 列出活动墓碑；支持在线/离线玩家、完整或可解析短 ID、位置、类型和剩余时间 | 部分实现；恢复后的缓存已可进入列表，但仅在线玩家筛选 |
| `/td info <ID>` | 支持完整 UUID 和无歧义短 ID；显示所有者、类型、实际位置、物品数、状态、创建/到期时间 | 部分实现；位置和类型数据已改善 |
| `/td remove <ID> [drop]` | 原子终结指定墓碑；可选是否掉落剩余物品；只能执行一次 | 部分实现 |
| `/td clear [drop]` | 批量终结活动墓碑，明确剩余物品策略并返回成功/失败数量 | 部分实现；当前固定不掉落 |
| `/td debug create` | 仅管理员玩家可创建测试墓碑，不从手中扣物品，并明确这是测试副本 | 已实现基础能力 |

所有命令反馈应来自 `lang.yml`，支持颜色和占位符；控制台与玩家均可使用非位置依赖的管理命令。

## 7. 非功能需求

### 7.1 可靠性

- NFR-001：所有会改变物品归属的操作必须在服务端主线程或经过安全快照后执行。
- NFR-002：终结墓碑和掉落物品的操作必须幂等。
- NFR-003：单个墓碑异常不得中断全量加载或清理任务。
- NFR-004：不得因配置重载、插件停用或服务器重启造成物品复制或丢失。

### 7.2 性能

- NFR-101：死亡和点击事件中不得执行全量文件扫描。
- NFR-102：周期清理的复杂度应与活动墓碑数量线性相关，并避免强制加载全部区块。
- NFR-103：单次持久化只写入发生变化的墓碑；全量保存使用不可变快照。
- NFR-104：目标规模基线为 1,000 个活动墓碑时，周期任务不产生可感知主线程卡顿。

### 7.3 兼容性与可维护性

- NFR-201：以 Paper 26.2 和 Java 25 为当前编译基线。
- NFR-202：Mannequin 能力以 Paper 26.2 的 `EntityType.MANNEQUIN`、玩家 Profile 和皮肤层 API 为基线，不承诺兼容缺少该实体的旧版本。
- NFR-203：存储类型通过统一接口扩展，核心生命周期不得包含类型特有的数据分支。
- NFR-204：配置、数据文件和命令输出具备版本或兼容策略。
- NFR-205：用户可见文案全部可本地化；日志包含墓碑 ID、玩家和失败阶段。

### 7.4 安全与权限

- NFR-301：所有管理命令服务端再次校验 `tracesdeath.admin`，补全只读与破坏性操作的审计日志。
- NFR-302：来自 PDC、YML 和命令参数的 UUID、世界、坐标、存储类型和物品数据均需校验。
- NFR-303：管理员绕过所有者限制必须通过明确权限节点，而非默认等同 OP 行为。

## 8. 配置需求

保留当前配置结构，但需遵守以下规则：

- 配置项只有在代码中具有完整行为和测试时才能出现在稳定版默认配置中。
- 类型相关行为读取墓碑创建时保存的 `storageType`，不能读取当前全局选择来判断旧墓碑。
- `cleanup-interval-seconds` 当前最小值为 10 秒，应在注释中明确。
- `warn-time-seconds` 应小于过期时间；不满足时告警并调整或禁用预警。
- `custom_entity` 未可用时，启动或重载应明确告警；创建失败后保留原生掉落。
- `mannequin` 应明确最低服务端版本；其 `interaction.mode`、`click-type`、`auto-equip`、`conflict-handling`、`auto-remove-when-empty`、`lava-proof` 和 `buoyant` 只有在实体路径真实使用后才算有效配置。
- 建议新增：数据格式版本、自动保存周期、管理员绕过权限、孤儿墓碑处理策略、GUI 是否允许存入、实验性类型开关。

## 9. 优先级与发布建议

### P0：物品安全与方块主链路

1. 在已完成实际位置记录、停服保存和索引重建的基础上，补充容器校验、迁移和回归测试。
2. 保证 GUI 全量可见、禁止意外存入并处理并发访问。
3. 修复直接领取的部分堆叠和剩余量处理。
4. 消除矿车原生库存、尸体 PDC 库存与缓存并存的数据分叉。
5. 增加创建、领取、过期、移除、重启恢复的自动化测试。

### P1：公开配置闭环

1. 完整落实 `tracesdeath.use`、`owner-only`、管理员绕过、`allow-break` 和 `explosion-proof`。
2. 实现过期预警、孤儿校验和完整本地化。
3. 让交互、保护和自动移除按单个墓碑持久化类型读取配置。
4. 完善管理命令的离线玩家、短 ID、物品数和批量清理策略。
5. 明确或移除 `buoyant` 与 `clear-drops=false` 等高风险/未实现选项。

### P2：实体墓碑

1. 将矿车、尸体和 Mannequin 完整接入统一缓存、交互、权限、清理与恢复链路。
2. 处理实体移动、区块卸载、重启实体定位、展示装备安全和重复实体去重。
3. 完成实体类型专项压力与物品守恒测试后，再标记为稳定。

### P3：扩展生态

- 通用自定义实体、地图坐标提示、领地插件兼容、数据库后端和跨服能力。

## 10. 核心验收用例

| 编号 | 前置条件 | 操作 | 预期结果 |
|---|---|---|---|
| AC-001 | 默认方块模式，玩家有物品 | 玩家死亡 | 附近生成一个墓碑；原生掉落被清除；墓碑内物品与死亡掉落完全一致 |
| AC-002 | 放置范围无安全位置，关闭强制放置 | 玩家死亡 | 不创建墓碑，不清除原生掉落，不丢失任何物品 |
| AC-003 | GUI 中含超过分类槽容量的物品 | 打开并关闭 GUI | 所有物品均可见或可翻页；未操作物品数量和元数据不变 |
| AC-004 | 两名玩家同时尝试打开同一墓碑 | 同时取走同一件物品 | 最多一人获得该物品，服务端和磁盘状态一致 |
| AC-005 | 背包只有部分堆叠空间 | 使用直接领取 | 可容纳数量进入背包，实际剩余数量按策略留存或掉落 |
| AC-006 | `owner-only=true` | 非所有者、所有者和绕过管理员分别打开各类墓碑 | 非所有者被拒绝；所有者和具有绕过权限的管理员可访问并留下审计日志 |
| AC-007 | 活动墓碑尚未到期 | 正常停止并重启服务器 | 墓碑仍存在，可查询、领取和按原创建时间到期 |
| AC-008 | 墓碑剩余物品且即将到期 | 等待提醒和到期 | 所有者只收到一次提醒；物品只掉落一次或按配置销毁；数据与容器均移除 |
| AC-009 | 配置从 `block` 重载为其他类型 | 操作重载前创建的方块墓碑 | 旧墓碑仍按 `block` 配置和提供者正确交互、保护与清理 |
| AC-010 | 存在损坏数据文件 | 启动服务器 | 其他墓碑正常恢复；损坏文件被隔离；日志提供可定位信息 |
| AC-011 | 管理员执行 remove/clear | 重复执行相同终结操作 | 第一次按策略处理，后续不再次掉落或复制物品 |
| AC-012 | 无 `tracesdeath.use` 权限 | 玩家死亡 | 完全保留原生死亡和掉落行为 |
| AC-013 | `storage.type=mannequin` | 玩家带装备死亡并取空墓碑 | 生成正确皮肤和姿势的模型；全部遗物仅能领取一次；清空后模型和缓存均按配置移除且展示装备不掉落 |
| AC-014 | 尸体或 Mannequin 配置为 `DIRECT_COLLECT` | 按配置点击实体 | 不打开 GUI，按自动装备和冲突策略领取；不匹配的点击无操作 |
| AC-015 | 重启时世界容器已丢失或存在重复实体 | 启动恢复 | 系统识别异常，不把无容器数据静默视为健康活动墓碑，并按配置修复或隔离 |

| 矿车清理 | 清理时不再额外主动掉落矿车原生库存 | 降低管理清理的重复掉落风险，但未解决玩家可从原生库存与缓存各取一次的问题 |

### 11.2 发布稳定版前的关键差距

1. 矿车仍把物品放入实体原生库存，同时管理器又保存完整缓存；玩家原生取走后缓存不变，仍存在复制风险。
2. 尸体实体交互已改用缓存，但提供者仍把同一批物品写入实体 PDC；超过 54 个物品时还会额外掉落溢出项，数据模型仍未真正单一化。
3. GUI 分类布局最多展示 9 个装备类和 36 个普通物品，未展示内容可能在关闭同步时被覆盖丢失。
4. GUI 缺少墓碑级并发锁和只取不存的完整限制。
5. 方块交互和 GUI 自动移除仍按当前全局 `storage.type` 读取配置；实体交互则固定打开 GUI，未使用实体类型的 `click-type`、`mode`、自动装备和冲突策略。
6. `owner-only` 只覆盖方块、尸体和 Mannequin，没有覆盖矿车，也没有管理员绕过权限；拒绝文案仍为硬编码。
7. `allow-break`、`explosion-proof`、过期预警和实际浮力未实现；实体攻击目前无条件取消，不能体现 `allow-break=true`。
8. `tracesdeath.use` 未校验，`ignore-keep-inventory=true` 仍依赖事件掉落列表。
9. 启动恢复虽已重建活动索引，但未验证方块/实体是否仍存在，也没有处理区块未加载、重复实体、旧数据缺少类型或数据格式迁移。
10. Mannequin 展示装备的异常死亡、外部移除、区块卸载和掉落行为尚未验证；实体自身无敌也可能使 `lava-proof=false` 和允许破坏失效。
11. 创建仍不是原子事务，YML 保存也未使用临时文件和原子替换。
12. 管理命令与部分玩家消息仍为硬编码文本；语言文件尚未覆盖完整交互。
13. 仓库仍没有测试源码，以上“已实现”状态主要来自静态代码审阅和编译验证。

## 12. 测试要求

至少建立以下测试层次：

- 单元测试：配置解析、物品差额计算、状态转换、过期时间、存储类型迁移和短 ID 解析。
- MockBukkit 或等价集成测试：死亡创建、GUI/直接领取、权限、清理、恢复与命令。
- Paper 测试服回归：重启恢复、区块卸载、爆炸/火焰/漏斗/活塞、多人并发和 Mannequin 展示装备安全。
- 每种稳定存储类型执行物品守恒矩阵：创建成功、创建失败、部分领取、清空、过期掉落、过期销毁、管理员移除和两次重复终结。
- 对未提交改动增加专项回归：搜索半径内实际位置、重载前后类型变化、正常停服恢复、缺失容器恢复、Mannequin 清空和异常移除。

发布门槛：P0、P1 对应验收用例全部通过，且不存在已知物品复制或无恢复路径的数据丢失问题。

## 13. 待产品确认事项

以下事项会改变玩法或数据语义，需要在实现前确认：

1. 墓碑是否必须保留死亡前的原始槽位，以支持一键恢复原布局。
2. `clear-drops=false` 是否确实用于允许复制物品；若不是，应删除并固定在成功后清除。
3. GUI 是否允许玩家向墓碑存入物品；本文默认“不允许”。
4. 墓碑被允许破坏时，剩余物品应掉落、转交破坏者、保留为孤儿数据还是禁止破坏。
5. 正常停服时墓碑方块/实体是否保留在世界；本文默认保留并在重启后恢复管理。
6. 实验性矿车、尸体和 Mannequin 是否继续对普通服主公开，还是在稳定前通过配置隐藏。
7. Mannequin 身上的装备是否只用于外观；本文默认是不可交互、永不掉落的视觉副本。
